# 코드 리뷰

> 작성일: 2026-06-14
> 브랜치: `develop`

기능 동작이 검증된 시점에서 **"구조가 옳게 서 있는가"** 를 점검하기 위해 진행한 코드 리뷰 라운드의 개요다.
AI 보조 리뷰(Claude Code)를 함께 활용하되, 모든 지적은 직접 검토한 뒤 반영 여부를 판단했다.
개별 현상·원인·해결 코드는 [트러블슈팅](troubleshooting.md)에 상세히 기록했고, 이 문서는 리뷰의 **관점·범위·결과**를 정리한다.

---

## 리뷰 방식

- **범위** — `pages/`(POM·컴포넌트), `tests/`, `conftest.py`, 설정(`pytest.ini`·`pyproject.toml`·`requirements.txt`), CI
- **관점** — 기능이 아니라 *구조*를 본다
  - POM 추상화가 새지 않는가 (테스트에 셀렉터 문자열이 노출되는가)
  - 죽은 코드·미사용 헬퍼가 골격의 신뢰도를 떨어뜨리지 않는가
  - 셀렉터·대기 전략이 negative 시나리오까지 견디는가
  - 버전·설정 고정으로 CI 재현성이 보장되는가
- **게이트** — 각 수정 후 `ruff check` / `ruff format` / 전체 테스트(11 TC) 통과 확인

## 설계 결정 — 프레임워크가 주는 기능은 다시 만들지 않는다

리뷰 과정에서 함께 되짚은, 초기 설계 단계의 판단 하나.

초기에는 `conftest.py`에서 `--browser`·`--headed`·`--browser-channel` 옵션과 `browser`/`context`/`page` 픽스처를 직접 재정의하려다 **argparse 충돌**을 만났다. 확인해 보니 `pytest-playwright`가 이미 이 옵션과 픽스처를 모두 제공하고 있었다.

→ 재정의 대신 **내장 기능을 그대로 활용**하기로 결정했다. 현재 `conftest.py`는 내장 `page` 픽스처 위에 `login_page`·`authenticated_page`·실패 스크린샷 훅만 얹는다. 크로스 브라우저(Edge 포함, `--browser chromium --browser-channel msedge`)도 별도 코드 없이 옵션만으로 처리된다.

**교훈**
프레임워크가 이미 제공하는 기능을 다시 구현하면 충돌과 유지보수 비용만 늘어난다. 가장 견고한 코드는 *작성하지 않은 코드*다 — 무엇을 직접 만들고 무엇을 라이브러리에 맡길지 경계를 긋는 것도 설계다.
